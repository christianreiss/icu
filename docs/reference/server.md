# ICU Server — Referenz

Stand 2026-09-28. Normative Grundlage: `protocol.md`. Entscheidungen und Belege in `../research`.

## 1. Zweck und Grenzen

Ein Prozess, ein Raum, ein UDP-Port. Der Server terminiert QUIC/mTLS, verwaltet die Teilnehmerliste, relayt Audio-Datagrams und Video-Streams ohne Decode, stellt Client-Zertifikate aus und widerruft sie. Er hat keine Channels, keine Rollen, kein Web-UI, keine Datenbank außer einer TOML-Datei. Admin-Bedienung ist die CLI desselben Binarys.

## 2. Artefakt und Umgebung

| Punkt | Festlegung |
| --- | --- |
| Binary | `icu-server`, Rust, Target `x86_64-unknown-linux-musl`, vollstatisch (`docs/research/cross-compile.md`). Build über rustup-Target oder Container; das Fedora-`rust`-Paket hat keine musl-Std. Profil `release-server` (2026-09-26): `release` mit `panic = "unwind"`, weil `panic` nur je Profil, nicht je Paket gesetzt werden kann und der Client bei `abort` bleibt. Ein Panic beendet so nur seinen Task: `spawn_logged` beobachtet jeden gestarteten Task und protokolliert einen Panic, statt ihn mit dem fallengelassenen `JoinHandle` zu verlieren, und `session::Seat` nimmt eine Sitzung, deren Task sich abwickelt, aus dem Raum (Close mit `SHUTDOWN`, der Client verbindet neu). Alle `std`-Mutexe im Server erholen sich von Poisoning (`lock`, `Room::lock`), der Store liegt hinter einem tokio-Mutex, der nicht vergiftet. Mit `panic = "abort"` gebaut (etwa schlicht `cargo build --release`) fehlt all das; der Server läuft, warnt aber beim Start, dass ein Panic in einer Sitzung dann den ganzen Server beendet (`cfg!(panic = "abort")`, Folgereview 2026-09-26). Ein `compile_error!` ginge nicht: `cargo build --release --workspace` baut den Server mit. |
| Laufzeitabhängigkeiten | keine (kein libc, kein CA-Bundle; der Server ist seine eigene CA). |
| Crypto | rustls 0.23 mit ring (Spike 1). |
| Installation | systemd-Unit (unten), `StateDirectory=icu` → `/var/lib/icu/`. Optional Docker `FROM scratch`. |
| Port | UDP 4711 Default, konfigurierbar. Bei Port < 1024 `AmbientCapabilities=CAP_NET_BIND_SERVICE`. |

## 3. Architektur

Der Workspace enthält `icu-proto`, `icu-server` und `icu-client`.
`icu-server` stellt `run(Config) -> Handle` für In-Process-Integrationstests
bereit; `main.rs` ist der CLI-Einstieg. Zertifikate und Zustand liegen in
`ca.rs` und `store.rs`, Verbindungen in `endpoint.rs` und `session.rs`,
Medienverteilung in `room.rs` und `relay.rs`, Verwaltung in `admin.rs`,
`cli/` und `shell/`. Quellcode und Tests liegen gemeinsam im Crate.

## 4. Konfiguration `/etc/icu/server.toml`

```toml
[server]
listen = ["0.0.0.0:4711", "[::]:4711"]
server_name = "icu.example.org"      # SNI im Server-Cert, steht auch im CN der CA; fehlt er: Name aus dem CN einer bestehenden CA, sonst der per DNS bestätigte FQDN des Hosts; gesetzt muss er zum CN einer bestehenden CA passen (§6.1 Schritt 2)
public_host = "icu.example.org:4711" # steht als URI-SAN icu://… in jedem Client-Cert
max_users = 16                       # 1..=64; Server validiert die Obergrenze beim Start
min_client = "0.1.0"                 # SemVer; ältere Clients schließt der Server beim Hello mit VERSION_UNSUPPORTED
admin_socket_group = "icu"           # Gruppe, der /run/icu/admin.sock gehört — volle Verwaltung
#monitor_socket_group = "icu-monitor" # optional: Gruppe von /run/icu/monitor.sock, der nur `status` beantwortet (§5); ohne die Zeile gibt es den Socket nicht

[limits]                             # Defaults aus docs/reference/protocol.md §7, überschreibbar
audio_datagrams_per_s = 110
control_msgs_per_s = 50
video_kbit_s = 400
enroll_per_ip_per_min = 5
enroll_global_per_min = 20

[tls]                                # jeweils 1 bis 36 500 Tage
ca_validity_days = 3650
client_validity_days = 365
server_validity_days = 365

[log]
level = "info"                       # tracing-Filter
format = "text"                      # oder "json"

[backup]                             # State-Snapshots (2026-09-27); ohne den Abschnitt gelten diese Defaults, also an
keep = 30                            # so viele bleiben, die ältesten gehen zuerst; 0 = keine automatischen
settle_ms = 5000                     # Wartezeit nach einer Änderung: eine Aktion, ein Snapshot
# dir = "/srv/icu-backups"           # Default: backups/ im State-Verzeichnis; anderswo braucht die Unit ReadWritePaths=
```

State unter `/var/lib/icu/`: `ca.key` (0600), `ca.crt`, `com.key` (0600, seit 2026-09-27: der Com-Schlüssel, Base64 von 32 Byte, `protocol.md` §1; angelegt nur in einem nie benutzten State wie die CA, sonst startet der Server ohne ihn nicht), `server.key` (0600), `server.crt`, `users.toml`, `state.lock`, dazu `server.crt.retired`, solange ein ersetztes Server-Leaf noch nicht auf der CRL steht (§5 `rotate-server-cert`). `invites.toml` und `invite.key` von vor 2026-09-24 werden ignoriert und können weg. Alle Schreibzugriffe atomar (Tempfile + fsync + rename + fsync des Verzeichnisses) und unter `flock(state.lock)`. Der Modus (0644, Schlüssel 0600) wird nach dem Anlegen exakt gesetzt, nicht nur über `open(2)`, das die umask schmälert; schreibt root (Offline-CLI), bekommt das Tempfile vor dem rename per `fchown` Besitzer und Gruppe des State-Verzeichnisses, ebenso ein neu angelegtes `state.lock` (`store::Owner::Dir`, 2026-09-27, externes Review S-2). Vorher entstanden unter der umask 027 eines gehärteten Hosts root-eigene 0640-Dateien, die der Dienst nicht lesen konnte: `Store::open` bzw. `Ca::load` scheiterten mit `EACCES`, `Restart=on-failure` lief in die Schleife. Nur `invite --out` schreibt für den Aufrufer (`write_private_for_caller`); die fsyncs laufen in `block_in_place`, damit ein langsames Storage nicht den Runtime-Worker samt quinn-Endpoint-Treiber blockiert (2026-09-24). Jede Änderung geht auf eine Kopie des Datenbestands, die Kopie wird geschrieben und erst danach übernommen — ein fehlgeschlagener Schreibvorgang lässt den laufenden Server also unverändert, statt einen Zustand zu bedienen, der nach dem nächsten Neustart weg ist.

Nutzermodell: ein Nutzer hat eine stabile `user_id` und über die Zeit **mehrere** Zertifikate (Renewal stellt ein neues aus; das alte und alle davor werden beim ersten Login des neuen widerrufen, `Store::retire_predecessors`, `superseded = true`, und fallen nach Ablauf aus Store und CRL). `UserRecord.name` ist seit 2026-09-22 nur noch ein **Spiegel** des Subject-CN des zuletzt ausgestellten Zertifikats (`protocol.md` §2.1); geschrieben wird er ausschließlich von `Store::add_user` (Registrierung ausstellen), `Store::redeem_registration` (Registrierung einlösen) und `Store::add_cert` (Renewal). `CertRecord.cn` hält den CN des jeweiligen Zertifikats, `CertRecord.renewed` den Zeitpunkt, zu dem dieses Zertifikat zuletzt für ein **Nachzügler**-Renewal benutzt wurde (§6.4). Beide sind `#[serde(default)]`, **`schema` bleibt 1, keine Migration**: Bestandsdatensätze laden mit `cn = ""`, was „unbekannt" heißt und nie „leerer Name" — die Zertifikats-DER werden nicht aufbewahrt, der CN lässt sich also nicht nachtragen. Die Angleichung passiert von selbst, pro Gerät, beim nächsten Connect (§6.4). `revoke` setzt `revoked` auf allen Certs des Nutzers — dauerhaft, kein Un-Revoke. `is_admin` erlaubt `CreateInviteRequest` und die Nutzerverwaltung (`protocol.md` §2.2/§2.3); gesetzt wird es für den ersten Nutzer, der seine Registrierung quittiert, solange kein quittierter Admin existiert (`Store::consume_registration`, §6.3; vorläufig schon bei Ausstellung gegen einen leeren Bestand und bei der Einlösung), danach über `promote`/`demote` (CLI, Admin-Socket) oder `AdminSetRole` (in-band, `protocol.md` §2.2 Variante 19) — `is_admin` fehlt in älteren `users.toml`-Dateien und deserialisiert dann als `false` (`#[serde(default)]`), keine Migration nötig. `disabled` ist eine zweite, unabhängige und **reversible** Login-Sperre (`disable`/`enable`, `AdminSetDisabled`): anders als `revoke` macht `enable` bestehende, nicht widerrufene Zertifikate sofort wieder nutzbar, keine erneute Anmeldung nötig; auch hier `#[serde(default)]`, keine Migration nötig. `server_muted`/`server_deafened` (2026-09-25) halten das vom Admin erzwungene Stumm-/Taubschalten (`mute`/`unmute`/`deafen`/`undeafen`, `AdminSetRestriction`): `session.rs` gibt sie beim Join als `Member.forced` in den Raum, `Room::apply_client_state` ODERt sie in jede Client-Anfrage, `Room::set_forced` setzt sie live; nur geschrieben, wenn `true`, sonst `#[serde(default)]`. `session::restriction_flags` macht aus `server_deafened` auch MUTED, und `Room::video_receivers` lässt einen so taubgeschalteten Nutzer aus (2026-09-26). `admin::set_restriction` schreibt den Store, setzt `forced` im Raum und pusht `UserRestrictionChanged`/`UserState` in einem Zug unter dem Store-Lock, das neue Paar aus dem alten unter demselben Lock berechnet (`mute` lässt `deafened`, wie es gerade ist); `serve` pusht beim Join, bevor es das Store-Lock freigibt. Beide Aktionen sind gegen das Entfernen des letzten funktionsfähigen Admins geschützt (§6.4).

`users.toml`:

```toml
schema = 1
next_user_id = 3

[user.1]
name = "alice"
created = "2026-09-20T12:00:00Z"
is_admin = true
disabled = false

[[user.1.cert]]
fingerprint = "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"  # SHA-256(Leaf-DER), lowercase hex
cn      = "alice"                    # Subject-CN dieses Zertifikats; "" = vor der Umstellung ausgestellt
issued  = "2026-09-20T12:00:00Z"
expires = "2027-09-20T12:00:00Z"
revoked = false
# renewed = "..."                    # nur gesetzt, wenn damit ein Nachzügler-Renewal lief
# superseded = true                  # widerrufen, weil ein Nachfolger sich angemeldet hat
```

`CertRecord.registration = true` markiert ein Registrierungszertifikat (`protocol.md` §2.3): der Nutzer ist eingeladen, hat sich aber noch nicht registriert. Widerrufen wird es erst, wenn der Client das neue Zertifikat quittiert oder zum ersten Mal damit einloggt (§6.3); ein nie quittiertes verschwindet nach Ablauf samt Nutzer — auch nach einer unquittierten Einlösung, deren Zertifikat womöglich nie ankam; wer es doch gespeichert, aber bis zum Ablauf des Bundles nie eingeloggt hat, braucht eine neue Einladung — (beim Start und bei jeder neuen Ausstellung), damit der Platzhaltername und der Admin-Platz eines leeren Bestands wieder frei werden. Ein Invite-Verzeichnis gibt es nicht mehr.

Zeitstempel durchgehend RFC 3339 in UTC; Fingerprints lowercase Hex ohne Trenner; `schema` erlaubt spätere Migrationen.

Atomare Schreibvorgänge verwenden exklusiv erzeugte, zufällig benannte Dateien (`.icu-*`) im selben Verzeichnis, mit den Zielrechten bereits bei der Erstellung. Vorhersehbare `.name.tmp`-Dateien werden nicht wiederverwendet oder als Symlinks verfolgt; private Schlüssel und CLI-Bundles bleiben 0600. Fehler vor dem Rename entfernen die neue temporäre Datei automatisch. Die systemd-Unit setzt zusätzlich `UMask=0077`.

**State-Backups** (2026-09-27, `backup.rs`). Der Server sichert seinen State selbst: beim Start und `backup.settle_ms` nach jeder Änderung — jedem Schreiben von `users.toml` (`Store::changes`) oder einer Zertifikatsdatei (`Ca::changes`) — einen Snapshot nach `Config::backup_dir` (`backup.dir`, sonst `<state_dir>/backups`); die neuesten `backup.keep` bleiben. Ein Snapshot ist ein Verzeichnis `YYYYMMDDTHHMMSSZ[-n]` (0700) mit Kopien von `ca.crt`, `ca.key`, `com.key`, `users.toml` und, falls vorhanden, `server.crt`, `server.key`, `server.crt.retired` (alle 0600) sowie einem `MANIFEST` (TOML: Format, Zeit, Anlass `start`/`change`/`shutdown`/`manual`/`pre-restore`/`restore`, Serverversion, `schema`, Nutzerzahl, Fingerprint, SHA-256 je Datei). Er entsteht unter `.icu-*` und wird erst vollständig umbenannt; die Namen sortieren nach der Zeit, ein neuer immer hinter den neuesten (auch wenn Aufräumen einen Namen derselben Sekunde frei gemacht oder jemand die Uhr zurückgestellt hat). Gelesen wird unter Store- und dann CA-Lock, also nie die Mitte einer Rotation; die Wartezeit fasst deren fünf Schreibvorgänge zu einem Snapshot zusammen. Neu ist ein Snapshot nur, wenn sich der Fingerprint gegenüber dem neuesten ändert, und `crl_number` zählt dabei nicht mit: sie ändert sich bei jedem Start und jedem CRL-Neubau, sonst schöbe jeder Neustart den Stand vor einem Fehler aus dem Fenster. Eine ältere CRL-Nummer zurückzuspielen ist harmlos, sie fällt nie unter die Uhr (`Store::next_crl_number`). Die Offline-CLI sichert ihre eigene Änderung selbst (`cli::dispatch`); eine beim Stopp noch wartende Änderung sichert der Server auf dem Weg hinaus. Jeder Schreiber des Backup-Verzeichnisses hält `flock(state.lock)`. Scheitert ein Snapshot, läuft der Server weiter; `status` meldet `backup.failed = 1` samt `error`, der Checkmk-Check `ICU_Backup` geht auf WARN. Wer als root schreibt (Offline-CLI, `restore`), gibt neue Dateien und Verzeichnisse dem Besitzer des State-Verzeichnisses (`backup::match_owner`): systemd korrigiert unter `DynamicUser` Besitzer nur, wenn schon die Spitze von `StateDirectory` nicht passt, und ein root-eigenes `ca.key` mit 0600 ließe den Dienst nicht starten. Die Snapshots liegen auf derselben Platte wie der State; gegen deren Verlust hilft nur eine Kopie woandershin (`deploy/README.md` „Backup und Restore“).

## 5. CLI

| Kommando | Wirkung |
| --- | --- |
| `icu-server run [--config PATH]` | Server starten; beim ersten Start CA und Server-Leaf erzeugen. |
| `icu-server setup [--config PATH]` | Interaktives Erstinbetriebnahme-Setup: fragt `server_name`, `public_host`, UDP-Port, `max_users` und `admin_socket_group` ab (bestehende Werte aus `PATH` als Vorgabe, sonst der Default bzw. der erkannte FQDN), validiert wie `run` (`Config::validate`, `reserved_names`) und schreibt `server.toml`; nichts geschrieben, wenn die Validierung scheitert. Bietet danach an, das erste Admin-Bundle auszustellen (`cli::invite::run`, wie `icu-server invite` — bootstrappt dabei CA, Com-Schlüssel und State-Verzeichnis genauso, ohne eigene Logik dafür). Rührt weder systemd noch die Firewall an, nennt am Ende nur die verbleibenden manuellen Schritte (`deploy/README.md`). Läuft auf einer noch nicht existierenden `PATH`. |
| `icu-server invite [--name neu-bob] [--ttl 24h] [--out datei]` | Registrierungs-Bundle ausstellen (`protocol.md` §2.3): Schlüssel + Registrierungszertifikat + CA + Com-Schlüssel als Passport, auf stdout oder mit Modus 0600 in `--out`. `--name` ist nur der Platzhaltername, bis der Eingeladene seinen eigenen wählt; ohne ihn wird `neu-xxxx` erzeugt. `--ttl` höchstens 7 Tage. Admin wird, wer als Erster eine Registrierung quittiert, solange es keinen bestätigten Admin gibt — nicht das zuerst ausgestellte Bundle (`protocol.md` §2.3); solange das so ist, weist `invite` auf stderr darauf hin (Antwortfeld `admin_confirmed`). Geht auch ohne laufenden Server. |
| `icu-server users` | Tabelle: `user_id`, Name, Fingerprint (gekürzt), ausgestellt, läuft ab, revoked, admin, disabled, pending (eingeladen, Registrierung nicht quittiert — `UserRecord::is_pending`), online. |
| `icu-server revoke <name\|user_id\|fingerprint>` | `revoked = true` auf **allen** Certs des Nutzers; eine laufende Verbindung wird sofort mit `KICKED` geschlossen. Danach neue CRL, ohne Neustart in Kraft (`endpoint::reload_tls`, §6.3): der nächste Handshake scheitert mit `certificate_revoked`. |
| `icu-server promote <name\|user_id\|fingerprint>` | `is_admin = true`. Pusht `UserAdminChanged { is_admin: true }` an jede eigene Sitzung des Nutzers, wenn online. |
| `icu-server demote <name\|user_id\|fingerprint>` | `is_admin = false`. Abgelehnt mit `LAST_ADMIN`, wenn der Nutzer der letzte funktionsfähige Admin ist. Sonst wie `promote`, mit `is_admin: false`. |
| `icu-server disable <name\|user_id\|fingerprint>` | `disabled = true`; eine laufende Verbindung wird sofort mit `AUTH_DISABLED` geschlossen. Abgelehnt mit `LAST_ADMIN`, wenn der Nutzer der letzte funktionsfähige Admin ist. |
| `icu-server enable <name\|user_id\|fingerprint>` | `disabled = false`; bestehende, nicht widerrufene Zertifikate sind sofort wieder gültig. |
| `icu-server kick <name\|user_id\|fingerprint>` | Schließt laufende Verbindungen mit `KICKED`, ändert nichts im Bestand; der Nutzer kann sich neu verbinden. |
| `icu-server mute\|unmute\|deafen\|undeafen <name\|user_id\|fingerprint>` | Setzt bzw. löst `server_muted`/`server_deafened`; wirkt sofort auf offene Verbindungen (`UserRestrictionChanged` an den Nutzer, `UserState` an alle) und übersteht Reconnect und Neustart. |
| `icu-server status` | Uptime, online, offene Verbindungen und laufende Handshakes (Momentanwerte), Verbindungen seit Start und Relay-Zähler (Summen seit Start). |
| `icu-server doctor [--json]` | Nur-Lese-Diagnose von Konfiguration, State, Zertifikaten, Admin-Socket, Listen-Ports und Snapshots; ein Befund je Prüfung mit `ok`/`info`/`skip`/`warn`/`fail` und am Ende die Summe, `--json` in der Form von `status --json` (stabile englische Schlüssel, `ok` ist die Aussage des Exit-Codes). Exit 1, sobald eine Prüfung `fail` ist; `warn` allein bleibt 0. Meldet vor dem Start, was §6.1 sonst erst beim Start als Fehler zeigt — CA-Name gegen `server_name`, fehlendes CA-Paar neben benutztem `users.toml`, gruppenlesbarer `server.key`, belegter Listen-Port, ein Socket-Pfad über `sun_path` (108 Byte; den Socket zu binden ist nicht fatal, der Server liefe also ohne Admin-Socket weiter) — und zwar alle in einem Durchgang statt einen je gescheitertem Start. Gehört zur Admin-Seite, ist also auch `icu-cli doctor`: es braucht weder einen gestoppten noch einen eingerichteten Server. **Schreibt nie und nimmt nie den State-Lock**: nicht über `cli::dispatch` (dessen Rückfall auf `Server::offline` würde `Store::open` aufrufen und damit Verzeichnis, `flock` und ein erstes `users.toml` anlegen), sondern direkt auf den Socket mit `admin::exchange`, Frist 10 s wie beim Checkmk-Check; `Config::read` statt `Config::load`, `users.toml` selbst geparst statt über `Store`, Zertifikate als Bytes gelesen statt die CA geöffnet. Als einziges Kommando liest es die Konfiguration selbst statt über die gemeinsame Lesung in `main` — sonst beendete eine kaputte `server.toml` genau das Kommando, das man ihretwegen aufruft. Was von hier aus nicht prüfbar ist, wird `skip` mit Grund: unter `DynamicUser` liegt der State hinter `/var/lib/private` (0700 root), und im `scratch`-Image gibt es weder `sh` noch `getent` oder `hostname`. Die Listen-Ports werden nur testweise gebunden, wenn der Socket `NotFound`/`ECONNREFUSED` sagt — `EACCES` und eine Zeitüberschreitung heißen, dass ein Server läuft und die Ports hält (2026-09-28). |
| `icu-server rotate-server-cert` | Neues Server-Leaf von derselben CA, sofort in Kraft (kein Neustart mehr); das alte kommt auf die CRL (`users.toml` `[[revoked_server]]`), damit Clients es ab ihrer nächsten Verbindung ablehnen — für den Fall, dass sein Schlüssel abhandengekommen ist. Clients brauchen nichts. Reihenfolge (2026-09-26): erst rotieren — das alte Leaf zuerst nach `server.crt.retired`, dann Schlüssel vor Zertifikat —, dann das alte Leaf auf die CRL. Scheitert die Rotation, bleibt das laufende Leaf unangetastet und kommt wieder aus der Datei — vorher stand es dann schon auf der CRL, und jeder Client lehnte den Server ab, bis eine Rotation gelang. Scheitert der CRL-Eintrag, wartet das alte Leaf in `server.crt.retired` auf die nächste Rotation oder den nächsten Start, der es von dort auf die CRL setzt; erst dann verschwindet die Datei (Folgereview 2026-09-26: vorher wartete es nur im Speicher, und ein Neustart oder Absturz verlor den Widerruf). Ausgeliefert wird das neue Leaf erst, wenn die TLS-Konfiguration neu geladen ist, und dafür braucht es ebenfalls einen Store-Schreibvorgang (CRL-Nummer); die Fehlermeldung sagt, welcher Teil in Kraft ist und welcher erst mit dem nächsten erfolgreichen Neuladen oder Start kommt. Ein Absturz zwischen den beiden Dateien hinterlässt ein Paar, das nicht passt, und der nächste Start repariert es (§6.1 Schritt 3); einer davor lässt das laufende Leaf in der Datei, und der Start streicht es dort wieder. Dasselbe (`admin::rotate_server_cert`) macht der Server selbst, sobald das Leaf weniger als `min(30, server_validity_days / 3)` Tage (mindestens 1) Restlaufzeit hat: `housekeeping` prüft beim Start und stündlich. Ebenso ein Leaf, das noch nicht gilt (`ca::leaf_not_yet_valid`, notBefore in der Zukunft; 2026-09-27, externes Review S-7): lief die Uhr bei einem Start vor (RTC vor NTP), rotierte der Server auf ein Leaf mit notBefore in der Zukunft und setzte das gute auf die CRL; nach der Korrektur lehnten die Clients es ab, bis die echte Zeit dort ankam. Jetzt ersetzt es die nächste stündliche Prüfung. Eine Uhr, die um weniger als die Laufzeit des Leafs nachgeht, verliert durch diese Rotation nichts: das neue Leaf gilt auch für richtig gehende Uhren. Bestehende Verbindungen behalten das alte Leaf bis zum nächsten Reconnect. Das CA-Zertifikat stellt `housekeeping` ein Jahr (höchstens `ca_validity_days / 3`) vor Ablauf mit demselben Schlüssel und Subject neu aus (`admin::renew_ca`, `Ca::renew_ca_cert`); ein Zertifikat, das nicht parst, gilt als fällig (2026-09-24). |
| `icu-server renew-ca` | Neues CA-Zertifikat auf demselben Schlüssel und Subject, sofort in Kraft; Clients brauchen nichts, weil der Vertrauensanker Subject + Schlüssel ist (`protocol.md` §2.3.3). |
| `icu-server backup [--list]` | Snapshot jetzt (Anlass `manual`, auch ohne Änderung seit dem neuesten), gibt den Pfad aus; über den Socket oder offline (§4 „State-Backups“). Die Antwort trägt nur den Pfad: die Socket-Gruppe darf den Server bedienen, aber nicht `ca.key` lesen. `--list` zeigt die Snapshots mit Zeit, Anlass, Nutzerzahl und Serverversion; es liest das Backup-Verzeichnis selbst, braucht also root. (2026-09-27) |
| `icu-server restore <verzeichnis\|latest>` | Spielt einen Snapshot zurück, nur bei gestopptem Server: nimmt `flock(state.lock)` selbst und geht nie über Socket oder `Server::offline`, die den Ziel-State öffnen und beschreiben würden. Prüft den Snapshot gegen sein `MANIFEST` (SHA-256 je Datei, Format, `schema`; ein Verzeichnis ohne `MANIFEST`, etwa eine Handkopie des State-Verzeichnisses, wird so genommen) und lädt ihn in einem Scratch-Verzeichnis `.icu-restore-*`, wie der Server es täte: `users.toml` samt Schema, CA-Paar, CA-Name gegen ein gesetztes `server_name`, Com-Schlüssel. Erst dann: den aktuellen State als Snapshot `pre-restore` sichern (ein Restore lässt sich also zurücknehmen), die Dateien atomar ersetzen (`server.crt.retired` behält, was es listet; ein fehlendes Server-Leaf stellt der Server neu aus), offline `rotate-server-cert` (vorher Runbook-Pflicht nach jedem Restore), Snapshot `restore`, Besitzer angleichen. `latest` ist der neueste Snapshot außer `pre-restore`, zweimal `restore latest` spielt also dasselbe zurück. Ein fehlendes State-Verzeichnis legt es an (neuer Host); `server_name` kommt dann aus der CA des Snapshots. (2026-09-27) |
| `icu-server shell` | Interaktive Admin-Shell im Cisco-IOS-Stil: persistenter Prompt, TAB-Vervollständigung, `?`-Kontexthilfe, Präfix-Abkürzungen (`sh us` → `show users`), Befehlshistorie. Details in §5.1. |
| `icu-cli [kommando]` | Zweiter Name desselben Binaries (Symlink `/usr/bin/icu-cli` → `icu-server`, im Container `/icu-cli`): alle Kommandos dieser Tabelle außer `run`, `restore` und `setup`, und ohne Kommando die Shell aus §5.1. |

**Nutzer-Selektor** (`<name|user_id|fingerprint>` oben): Name, `user_id` oder voller Fingerprint, ausdrücklich auch `id:<user_id>` oder `name:<name>` (`Store::resolve`, 2026-09-27). Ein Name darf nur aus Ziffern bestehen; vorher gewann die `user_id`, und `revoke 1` traf bei einem Nutzer namens „1“ den Nutzer mit ID 1, oft den Eigentümer (Readiness-Review 2026-09-27, S5). Jetzt zählt jede Lesart, auch der ganze Selektor als Name (ein Nutzer namens `id:3` wird also nicht still übergangen): trifft mehr als eine verschiedene Nutzer, lehnt der Server mit `AMBIGUOUS_USER` ab und nennt alle Treffer mit `user_id` und Namen. Die Antwort nennt den getroffenen Nutzer (`user_id`, `name`), die CLI gibt ihn aus („revoked alice (user_id 3), closed 1 connection(s)“); ein noch laufender älterer Server ohne `name` in der Antwort bekommt nur die `user_id` angezeigt.

Einladen geht auch über die authentifizierte `icu/1`-Verbindung (`CreateInviteRequest`, `protocol.md` §2.2) — ein eingeloggter Admin braucht dafür weder CLI noch Host-Zugriff, nur `Welcome.is_admin`. Alle drei Wege laufen über `registration::issue`.

**Wer schreibt den State.** Ein laufender Server ist der alleinige Schreiber von `users.toml`. Jedes CLI-Kommando außer `run` geht deshalb über den Admin-Socket; der Server führt die Änderung aus, persistiert sie und wendet sie sofort auf offene Verbindungen an. Nur wenn kein Server läuft (Socket nicht vorhanden — `NotFound`, auch für ein fehlendes `/run/icu` — oder `ECONNREFUSED`, die Datei, die ein Absturz hinterlässt), schreibt die CLI selbst und hält dabei `flock(/var/lib/icu/state.lock)`. Damit wirkt ein frisch ausgestelltes Bundle sofort statt erst nach dem nächsten Neustart, und CLI und Server können einander keine Änderung überschreiben. Jeder andere Socket-Fehler — `EACCES` für jemanden außerhalb der Socket-Gruppe, ein Server, der ohne Antwort auflegt — wird mit Pfad und Ursache gemeldet (`cli::dispatch`, 2026-09-27); vorher fiel die CLI bei jedem Fehler auf den State zurück und meldete dann nur `cannot lock … (is a server running?)` oder einen Lesefehler im State-Verzeichnis.

**Die CLI braucht nur den Socket** (2026-09-27, Readiness-Review S1). `run` und der Offline-Rückfall lesen die Konfiguration vollständig (`Config::load` = `Config::read` + `Config::resolve`); alle anderen Kommandos lesen nur die Datei (`Config::read`) und brauchen daraus den Socket-Pfad. Vorher löste jedes Kommando zuerst `server_name` auf, und ohne `server_name` — so die Paketkonfiguration — liest das `ca.crt` aus dem State, unter `DynamicUser` hinter `/var/lib/private` (0700 root): Mitglieder der Gruppe `icu` und der Checkmk-Agent bekamen „Permission denied“ statt `status`.

Admin-Socket: `/run/icu/admin.sock` (`RuntimeDirectory=icu`, `RuntimeDirectoryMode=0755`, Gruppe aus `admin_socket_group` — ein Name aus `/etc/group`, sonst eine gid, sonst was `getent group` beim NSS des Hosts findet (`admin::resolve_group`, 2026-09-27, externes Review: das statische musl-Binary hat kein NSS, und eine Gruppe nur aus FreeIPA/SSSD wurde mit einer Warnung übergangen; im `scratch`-Image ohne `getent` bleiben Name aus `/etc/group` und gid); unter der Unit gehört `/run/icu` per `Group=icu` derselben Gruppe, `admin_socket_group` ist dort also `icu`), JSON-Zeilenprotokoll, ein Request pro Zeile, eine Response pro Zeile, dann Close. Kein Netzwerk-Admin, keine Authentifizierung außer den Dateirechten des Sockets. Grenzen (2026-09-27, externes Review S-6; vorher las eine Verbindung beliebig lange Zeilen, beliebig viele Requests und ohne Frist, und die Gruppe des Sockets — auch der Checkmk-Agent — konnte den Server so bis `MemoryMax` wachsen lassen oder seine Deskriptoren belegen): eine Request-Zeile höchstens 64 KiB (`admin::MAX_REQUEST_LINE`, länger → `BAD_REQUEST` und Close), höchstens 16 Verbindungen zugleich (`admin::MAX_CONNECTIONS`; weitere warten im Listen-Backlog, ohne Deskriptor des Servers), für das Lesen des Requests und das Abnehmen der Antwort je `timing.admin_timeout_ms` (Default 10 s), dann Close. Nach der Antwort schließt der Server; jeder Client stellt genau eine Anfrage (CLI, darüber der Checkmk-Check). `admin::exchange` wartet höchstens 30 s auf die Antwort (`EXCHANGE_TIMEOUT`), der Checkmk-Check ruft `status` unter `timeout 10` auf. Scheitert `accept` (`EMFILE`, `ENFILE`, `ECONNABORTED`), protokolliert der Server das, wartet 10 ms bis 1 s (verdoppelnd, nach einem Erfolg wieder von vorn) und nimmt weiter an (2026-09-27, S7); vorher endete die Accept-Schleife beim ersten Fehler, und der Socket blieb bis zum Neustart tot.

**Monitoring-Socket** (2026-09-28). Ist `server.monitor_socket_group` gesetzt, öffnet der Server daneben `/run/icu/monitor.sock` (`paths.monitor_socket`), 0660, Gruppe aus diesem Wert — dieselbe Auflösung wie beim Admin-Socket (`admin::resolve_group`). Derselbe Code bedient beide (`admin::listen_at`, Unterschied ist ein `Access`); die Ablehnung sitzt in `serve_one` hinter `serde_json::from_str`, so dass jeder später hinzukommende Request dort automatisch scheitert statt durchzurutschen: alles außer `Status` bekommt `{"ok":false,"error":"FORBIDDEN"}`. Auch `Users` — die Namen und Fingerprints der Nutzer sind kein Monitoring-Datum. Scheitert das Binden, läuft der Server weiter (Warnung), wie beim Admin-Socket. Ohne die Einstellung entsteht kein Socket, und für bestehende Installationen ändert sich nichts. `RuntimeDirectoryMode` ist deshalb 0755 statt 0750: `/run/icu` gehört per `Group=icu` der Admin-Gruppe, durch ein 0750-Verzeichnis käme eine reine Monitoring-Gruppe nie an ihren Socket; im Verzeichnis liegen nur die beiden Socket-Dateien, und jede ist mit 0660 und ihrer eigenen Gruppe selbst das Tor. `cli::dispatch` versucht bei `EACCES` auf dem Admin-Socket **und nur für `Status`** den Monitoring-Socket; `NotFound`/`ConnectionRefused` führen unverändert in den Offline-Rückfall, der Monitoring-Socket nie. Damit läuft der ausgelieferte Checkmk-Check ohne Schalter für einen Agenten, der nur in `monitor_socket_group` ist (`deploy/README.md` §5).

Fehlerform einheitlich `{"ok":false,"error":"<kurzform>","detail":"<text>"}`; ein unbekannter Selektor ist `NO_SUCH_USER`, ein mehrdeutiger `AMBIGUOUS_USER`. `user_id` und `name` in den Antworten sind 2026-09-27 dazugekommen (nur Felder ergänzt, keine umbenannt).

**Kein `rename` mehr** (entfallen 2026-09-22): der Name steht im Zertifikat, und der Server kann keinen Schlüssel für einen Nutzer erzeugen — umbenennen kann sich also nur der Nutzer selbst, über ein Renewal (`protocol.md` §2.2 Nr. 9). Muss ein Admin trotzdem eingreifen (anstößiger Name, Tippfehler, von Hand verkorkster Bestand): Server stoppen, `UserRecord.name` in `users.toml` editieren, Server starten. Der nächste Connect dieses Nutzers ist dann ein CN-Mismatch, und sein Client zieht selbsttätig nach — Notausgang und Nachzügler-Mechanismus sind dasselbe. Als härtere Mittel bleiben `revoke` plus neues Bundle.

### 5.1 Shell

`icu-server shell` (`crates/icu-server/src/shell/`) ist keine eigene Art
Admin-Client: jeder Befehl geht wie bei den einzelnen CLI-Kommandos über
`cli::dispatch` — ein Request, eine Response, dann Schluss (§5 oben); die
Shell hält keinen Dauerzustand über den Admin-Socket und ändert nichts am
Protokoll. `run`, `restore` und `setup` sind absichtlich nicht Teil der
Shell: `restore` braucht einen gestoppten Server und nimmt `flock` direkt,
was mit einer laufenden Sitzung auf demselben Socket nicht zusammengeht,
`run` ist der Dienst selbst, und `setup` richtet den Host ein, bevor es
überhaupt einen Socket gibt.

Verben (Cisco-artig, mit TAB-Vervollständigung und eindeutigen
Präfix-Abkürzungen wie bei Cisco IOS, z. B. `sh us` für `show users`):

| Befehl | Wirkung |
| --- | --- |
| `show status [--json]` | wie `icu-server status` |
| `show users [--json]` | wie `icu-server users` |
| `show backups` | wie `icu-server backup --list` |
| `doctor [--json]` | wie `icu-server doctor`, lokal und nur lesend: kein Admin-Request, und ein `fail` beendet die Sitzung nicht, wie es die einmalige CLI beendet |
| `invite [name] [ttl] [out-file]` | wie `icu-server invite --out`; mit einer Ausgabedatei landet das Bundle dort (Modus 0600) statt auf stdout |
| `kick`/`disable`/`revoke <user>` | wie die gleichnamigen CLI-Kommandos, fragen vorher `[y/N]` (schließen Verbindungen bzw. `revoke` ist unumkehrbar) |
| `mute`/`unmute`/`deafen`/`undeafen`/`promote`/`demote`/`enable <user>` | wie die gleichnamigen CLI-Kommandos |
| `rotate-server-cert` / `renew-ca` / `backup` | wie die gleichnamigen CLI-Kommandos |
| `refresh` (Kurzform `r`) | holt die Nutzerliste für die Vervollständigung neu |
| `help` / `?` | listet alle Befehle |
| `exit` / `quit` | verlässt die Shell |

Präfix-Abkürzung gilt nur für literale Schlüsselwörter, nie für einen
Nutzer-Selektor oder Freitext: ein Nutzer namens `k` wird nie mit `kick`
verwechselt. Ein Treffer, der genau passt, gewinnt immer sofort (die
Kurzform `r` bleibt also `refresh`, obwohl sie auch Präfix von `revoke`,
`renew-ca` und `rotate-server-cert` ist); sonst gewinnt ein eindeutiges
Präfix, mehrdeutige Eingaben nennen alle Treffer (wie `AMBIGUOUS_USER` beim
Nutzer-Selektor). Ein Leerzeichen vor `?` oder am Zeilenende zeigt, ohne die
Zeile abzuschicken, was an der Stelle gültig wäre — Nutzernamen werden dabei
aus einer Momentaufnahme der letzten `users`-Antwort vervollständigt, nicht
live pro Tastendruck: sie wird beim Start geholt, nach jedem ändernden
Befehl neu geholt und mit `refresh`/`r` von Hand.

**`icu-cli`** (2026-09-28) ist kein zweites Programm, sondern derselbe
Prozess unter einem zweiten Namen: das Paket legt `/usr/bin/icu-cli` als
Symlink auf `icu-server`, und `main.rs` sieht nur auf `argv[0]`
(`is_cli_name`). Ohne Kommando startet es die Shell, mit einem Kommando tut
es genau das, was `icu-server <kommando>` täte. Gewählt gegen ein zweites
`[[bin]]`, weil das Release-Binary statisch gegen musl gelinkt ist und das
Paket sonst doppelt so groß würde. `run`, `restore` und `setup` gibt es dort
nicht: sie sind zwar noch geparst, antworten aber nur mit dem Hinweis auf
`icu-server …` und Exit 2, statt mit clap's „unrecognized subcommand"
(`#[command(hide = true)]`, also nicht in `icu-cli --help`). Prompt
(`icu-server> `) und Historie bleiben dieselben — es ist dieselbe Shell,
nicht eine zweite.

Menschliche Ausgaben der Shell und der einzelnen Admin-Kommandos nutzen
dieselben Statusgruppen und Nutzer-/Backup-Ansichten. Bei schmalem Terminal
werden Tabellen zu mehrzeiligen Einträgen; alle Felder bleiben sichtbar.
Farbe erscheint standardmäßig nur auf einem Terminal (`TERM=dumb` oder
`NO_COLOR` schalten sie ab). `--color=always` erzwingt sie,
`--color=never` unterdrückt sie; die Option gilt auch nach einem Kommando,
z. B. `icu-cli users --color=never`. JSON-Antworten und Passport-Daten
bleiben immer unverändert und enthalten keine Farbsequenzen. Die Farbe
ergänzt die ausgeschriebenen Zustände und Befunde, ersetzt sie nicht.

Befehlshistorie liegt unter `$XDG_STATE_HOME/icu-server/shell_history`
(sonst `~/.local/state/icu-server/shell_history`), Modus 0600, je Nutzer,
nicht je Serverkonfiguration — die Shell läuft interaktiv unter wer auch
immer in der Socket-Gruppe ist oder root über SSH, nicht unter dem
`DynamicUser` des Dienstes. Fehlt `$HOME`, läuft die Shell ohne
persistente Historie weiter, statt den Start zu verweigern.

## 6. Ablauf

### 6.1 Start

1. Config laden, validieren: Listen-Adressen, `server_name` nicht leer — fehlt er in der Datei, setzt `Config::resolve` ihn (2026-09-26; seit 2026-09-27 nur für `run` und den Offline-Rückfall der CLI, §5): gibt es schon eine `ca.crt`, den Namen aus ihrem CN `ICU CA <name>` (eine CA mit CN nur `ICU CA` ist ein Startfehler), sonst den FQDN des Hosts (`hostname --fqdn`, ersatzweise der uname-Nodename), und nur, wenn er einen Punkt hat, weder `localhost*` noch Beispielname ist und per DNS auf mindestens eine Adresse auflöst, die weder Loopback noch Link-local ist und sich lokal binden lässt, also diesem Host gehört (`verify_fqdn`); sonst ein Startfehler mit Name, Adressen und Grund —, `1 ≤ max_users ≤ 64`, `min_client` als SemVer parsebar, und `max_users × 100 B + Reserve < 16 KiB` (sonst passt ein volles `Welcome` nicht in ein Control-Frame, `protocol.md` §7). Obergrenzen (2026-09-26): Laufzeiten unter `[tls]` höchstens 36 500 Tage, jeder Wert unter `[timing]` höchstens 3 600 000 ms — größere liefen in der Datums- bzw. Uhrzeitrechnung über, und das ist mit `panic = "abort"` kein Fehler, sondern ein Absturz bei jeder Registrierung. `ca::set_validity` rechnet zusätzlich mit `checked_add`. Für Beispiele reservierte Namen (`example.com`/`.net`/`.org` samt Subdomains, TLDs `.example`, `.invalid`, `.test`; `localhost` und IP-Adressen gehen) in `server_name` und im Host von `public_host` lehnt der Server dort ab, wo sie zum ersten Mal eingebacken würden (`Config::reserved_names`, 2026-09-26): beim Anlegen einer neuen CA (Schritt 2, beide Namen) und bei der ersten Einladung eines Servers ohne Nutzer (`public_host`, §6.3) — sonst backte ein `systemctl enable --now` oder ein erstes `invite` mit der ausgelieferten Beispielkonfiguration `ICU CA icu.example.org` in CA und Zertifikate. Mit einer bestehenden CA startet der Server trotzdem und warnt im Log; die Validierung selbst lehnt sie nicht ab (Folgereview 2026-09-26: dort legte die Prüfung eine Installation, deren CA einen solchen Namen schon trug, mit dem Update lahm, samt `status`/`users` und damit Checkmk).
2. CA laden oder erzeugen (`rcgen::CertificateParams` mit `IsCa::Ca(Constrained(0))`, `KeyCertSign|CrlSign`, P-256; Spike 2b). Eine neue CA heißt `ICU CA <server_name>` — daraus nimmt der Client das SNI (`protocol.md` §2.3). Eine bestehende CA bleibt, wie sie ist. **Nennt ihr CN einen anderen Namen als ein gesetztes `server_name`** (Groß-/Kleinschreibung zählt nicht), bricht `open_ca` ab, bevor irgendetwas ausgestellt wird, und nennt beide Werte samt Abhilfe (`server_name` auf den CA-Namen setzen oder weglassen; ein anderer Name heißt neue CA und alle registrieren sich neu) — für `run` und die Offline-CLI (2026-09-27, Readiness-Review S2). Vorher lief der Server weiter, und erst das nächste Server-Leaf (Auto-Erneuerung, `rotate-server-cert`, Reparatur beim Start) trug den neuen Namen: jeder Client scheiterte dann an `NotValidForName` und verband sich nicht mehr neu. Gewählt wurde der Abbruch statt eines Leafs auf den CA-Namen mit Warnung, weil ein Konfigurationswert, der still nicht gilt, beim nächsten Umzug wieder überrascht. Eine CA von vor dem Namen im CN (nur `ICU CA`) nennt keinen und wird nicht geprüft. **Erzeugt wird nur, wenn `ca.crt` und `ca.key` beide fehlen** (`NotFound`, 2026-09-26) **und der State nie benutzt wurde**: keine Nutzer, keine CRL-Nummer, kein widerrufenes Server-Leaf (`Store::is_fresh`, geprüft in `open_ca` über `Ca::load_or_create_if`, für `run` und die Offline-CLI; Folgereview 2026-09-26). Fehlen beide neben einer benutzten `users.toml` — ein unvollständiger Restore, eine Migration ohne die CA —, ist das ein Startfehler, der beide Dateien nennt und auf das Runbook „Backup und Restore“ in `deploy/README.md` zeigt; vorher entstand eine neue CA, und kein Client kam mehr durch den Handshake. Jede andere Lage — eine Datei verloren, nach einem Restore für den Dienst nicht lesbar, kaputt, Schlüssel passt nicht zum Zertifikat — ist ein Startfehler mit Klartext. Vorher legte jeder Lesefehler still eine neue CA an und benannte ihren Schlüssel über `ca.key`: alle Zertifikate, Passports und Bundles waren tot, der alte Schlüssel weg. Eine neue CA wird mit `warn` protokolliert; `create_ca` schreibt den Schlüssel vor dem Zertifikat.
3. Server-Leaf laden oder erzeugen (SAN = `server_name` und, falls IP, IP-SAN; EKU ServerAuth) über `CertificateParams::signed_by(&leaf_key_pair, &issuer)` — in rcgen 0.14 nimmt `signed_by` **Public Key und Issuer**, anders als die CSR-Variante in §6.3; Kette = Leaf + CA. Das Leaf ist entbehrlich: passt `server.key` nicht zu seinem SubjectPublicKeyInfo, stammt es nicht von dieser CA oder lässt sich eines von beiden nicht lesen, stellt der Server ein neues aus (`warn`) und setzt das gefundene auf die CRL (`Ca::take_retired_leaves`, `admin::record_retired_leaves`) — sonst hinge er nach einem Absturz mitten in einer Rotation in einer Neustartschleife. Wie bei jeder Rotation steht das gefundene Leaf vor dem neuen Paar in `server.crt.retired`; was die Datei listet, kommt beim Start auf die CRL, außer dem Leaf, das gerade als Paar geladen wurde.
4. `flock(state.lock)` nehmen und für die gesamte Laufzeit halten; `users.toml` laden (`schema` prüfen). Fehlt die Datei, legt `Store::open` sie leer an und schreibt sie sofort — aber nur, wenn im State-Verzeichnis auch sonst nichts liegt; neben `ca.crt`, `ca.key`, `server.crt`, `server.key`, `server.crt.retired` oder `com.key` ist sie verloren gegangen (ein Restore oder eine Migration ohne sie), und der Start bricht mit den gefundenen Dateien und dem Verweis aufs Runbook „Backup und Restore“ ab, ohne etwas zu schreiben (`store::first_users`, 2026-09-27, zweite Runde des externen Reviews). Vorher trat ein leerer Bestand an ihre Stelle: jeder Nutzer unbekannt, jeder Widerruf vergessen, CA und Com-Schlüssel liefen weiter. Weil `Store::open` vor `open_ca` und `open_com_key` läuft — auch in der Offline-CLI —, gibt es Schlüsselmaterial ohne `users.toml` nur nach einem Verlust. Danach nie quittierte, abgelaufene Registrierungen verwerfen. Ab hier ist der Server alleiniger Schreiber des States (§5).
5. rustls `ServerConfig` in **dieser** Reihenfolge — `builder_with_provider(rustls::crypto::ring::default_provider().into())` liefert `WantsVersions`, der Versionsschritt muss also vor dem Verifier kommen, sonst übersetzt es nicht:
   `ServerConfig::builder_with_provider(ring_provider)` → `.with_protocol_versions(&[&rustls::version::TLS13])?` → `.with_client_cert_verifier(WebPkiClientVerifier::builder(Arc::new(roots)).allow_unauthenticated().build()?)` → `.with_single_cert(vec![leaf, ca], key)?`; danach `alpn_protocols = [b"icu/1"]` und `max_early_data_size = 0`. Der Verifier steckt in `endpoint::ExpiredClientCertVerifier` (abgelaufene Client-Leaves, `protocol.md` §2.3.3), der zuerst jede mitgeschickte Zwischenzertifikat-Kette ablehnt (2026-09-26): Clients schicken nur ihr Leaf, jedes weitere Zertifikat wäre nur ein Kandidat für die Pfadsuche, also Signaturprüfungen auf Kosten des Servers vor jeder Authentifizierung.
6. quinn `ServerConfig` aus `QuicServerConfig::try_from(rustls_config)`; Transport wie `docs/reference/protocol.md §1`. Signaturhinweise: `max_idle_timeout(Some(IdleTimeout::try_from(Duration::from_secs(60))?))`, `datagram_receive_buffer_size(Some(64 * 1024))` (Option) gegen `datagram_send_buffer_size(64 * 1024)` (kein Option), `max_concurrent_uni_streams(VarInt::from_u32(2 * max_users + 4))`, `max_concurrent_bidi_streams(1)`. Flusskontrolle (2026-09-26, `protocol.md` §1): `stream_receive_window` 64 KiB, `receive_window` 1 MiB, `send_window` 1 MiB — quinns Defaults (1,25 MB je Stream, unbegrenzt je Verbindung, 10 MB Sendepuffer) ließen einen Teilnehmer ~47 MB binden. Auf `quinn::ServerConfig`: `max_incoming(1024)`, `incoming_buffer_size(64 KiB)`, `incoming_buffer_size_total(4 MiB)` statt 65 536 und 100 MiB. `migration(true)` liegt auf `quinn::ServerConfig`, nicht auf `TransportConfig`.
7. Ein `Endpoint` pro Listen-Adresse, gebaut über `icu_proto::com::endpoint`: der Socket ist in `ComSocket` gewickelt, der jedes Datagramm ohne gültiges Com-Tag verwirft, bevor quinn es sieht, und jedes ausgehende taggt (`protocol.md` §1, 2026-09-27); alle Endpoints zählen die Verwürfe in `Server.com_dropped` (`status`: `com_dropped`). Den Schlüssel lädt `open_com_key` aus `com.key` (Schritt 2 gilt sinngemäß: neu nur bei `Store::is_fresh`). Accept-Loop je Endpoint auf einem tokio-Multi-Thread-Runtime.
8. Admin-Socket öffnen (`/run/icu/admin.sock`, Gruppe aus `admin_socket_group`, Modus 0660). SIGTERM → allen `close(SHUTDOWN)`, 1 s warten, Socket und `state.lock` freigeben, Ende. Auf das Abklingen geschlossener Verbindungen (`wait_idle`) wartet der Server höchstens 3 s (2026-09-26): eine Verbindung, deren Peer nie antwortet — ein hängender Handshake, eine Flut —, bleibt drei Probe-Timeouts samt Backoff stehen und hielt ein Stoppen bis zu einer Minute auf. Danach wartet `Handle::shutdown` höchstens weitere 3 s, bis keine Task mehr eine Referenz auf den Serverzustand hält (2026-09-27): abgebrochene Tasks lassen sie erst los, wenn die Runtime sie erreicht, manche (Zertifikatsprüfung, Verbindungen) stehen gar nicht auf der Liste — ein Start im selben Prozess direkt danach fand `state.lock` noch belegt. Neben `housekeeping` läuft die Backup-Task (`backup::task`, 2026-09-27, §4 „State-Backups“): ein Snapshot des Start-Stands (keiner, wenn er dem neuesten gleicht), danach einer je Änderung; eine beim SIGTERM noch wartende Änderung sichert sie innerhalb der Wartezeit, bevor die Tasks enden.

### 6.2 Accept

**Eine Verbindung pro Zertifikat** (2026-09-24, `protocol.md` §7): nach `authenticate` trägt `session::LiveCert` die Verbindung samt `user_id` unter dem Leaf-Fingerprint ein — Raum-Sitzungen (auch solche vor `Hello`) in `Server.live_certs`, Registrierungs- und renew-only-Sitzungen in `Server.roomless` (2026-09-26; vorher hatten renew-only-Sitzungen gar keinen Platz). Stand dort schon eine andere, wird sie mit `SESSION_REPLACED` geschlossen (über `Room::close_connection`, das den Code vor dem Schließen im Member vermerkt, damit `UserLeft` ihn trägt); der Eintrag wird beim Ende nur entfernt, wenn er noch dieser Verbindung gehört (`stable_id`). `Server.roomless` hält höchstens `MAX_ROOMLESS_SESSIONS` (8) Einträge; eine weitere Sitzung, die keinen Eintrag ablöst, bekommt `SERVER_FULL` — der Raum begrenzt diese Sitzungen nicht. Eine Registrierung zahlt ihr Budget (§6.3) erst, wenn Platz ist, unter dem Lock der Tabelle und vor dem Eintrag (`LiveCert::claim`): mit `SERVER_FULL` abgewiesen, hat sie nichts verbraucht (Folgereview 2026-09-26; vorher kostete jeder Versuch ein Token, und die Wiederholungen des Clients endeten im fatalen `ENROLL_RATE_LIMITED`). Getrennte Obergrenzen für Registrierung und renew-only gibt es nicht: beide Arten brauchen ein gültiges Zertifikat, Registrierungen zusätzlich Budget und eine offene Einladung. Sie bekommen direkt nach der Anmeldung keinen Stream-Kredit mehr (`set_max_concurrent_{uni,bi}_streams(0)`), sie lesen nur ihren Control-Stream. Weil beide Tabellen die `user_id` kennen, schließen Widerruf, Deaktivieren und Kick über `session::close_user` jede Verbindung des Nutzers, nicht nur Raum-Sitzungen; `close_retired` schaut für abgelöste Zertifikate in beide.

```
incoming = endpoint.accept()                  // endpoint::admit
  if laufende Handshakes ≥ max_handshakes (256) → incoming.refuse()       // alle Endpoints
  if nicht validiert && laufende Handshakes ≥ 32 → incoming.retry()      // Adressvalidierung, kostet kein Budget
  if validiert && Quelle hält 4 Handshakes (IPv4 bzw. IPv6-/64; 16 je /48) → incoming.refuse()
  if limits.ip_bucket(/64 bzw. IPv4).exhausted || global_bucket.exhausted → incoming.refuse()
  if IP-Tabelle voll (4096) → validiert: nur globales Budget, sonst retry()
connecting = incoming.accept()                // ab hier ≤ 5 s bis Handshake-Ende, sonst verworfen
// handshake_data() nimmt &mut self und liefert Box<dyn Any>; Downcast auf quinn::crypto::rustls::HandshakeData
alpn = connecting.handshake_data().await?
         .downcast::<quinn::crypto::rustls::HandshakeData>()?.protocol   // Spike 2b: vor Handshake-Ende lesbar
conn = connecting.await                       // Handshake-Platz frei
if etablierte Verbindungen ≥ max_connections (256) → close(SERVER_FULL)
match alpn:
  icu/1        → session::handle(conn)
```

Laufende Handshakes und etablierte Verbindungen sind getrennte Zähler (`Server.handshakes`, `Server.open_connections`, 2026-09-26). Vorher zählte eine gemeinsame Grenze beides: wer die Retry aus drei IPv4-Adressen (oder einem IPv6-/62) beantwortete und dann nicht weitermachte, hielt je Quelle rund 100 Plätze für 10 s und sperrte alle anderen aus, Reconnects und Logins eingeschlossen. Jetzt hält eine validierte Quelle höchstens 4 Handshakes zugleich (`IpLimits::handshake_slot_free`), gebucht erst nach der Adressvalidierung — ein unvalidierter Handshake kann eine gefälschte Absenderadresse tragen und darf deshalb keiner Quelle angerechnet werden; unvalidierte begrenzt die Retry-Schwelle von 32. Eine eben fertige Verbindung über `limits.max_connections` bekommt `SERVER_FULL` (nicht fatal); das ist nur eine Rückfallebene, weil Unbekannte über den Handshake hinaus keine Verbindung halten und jedes Zertifikat höchstens eine.

### 6.3 Registrierung (`registration.rs`, `session.rs`)

Ablauf und Regeln normativ in `protocol.md` §2.3; hier nur die Umsetzung.

**Ausstellen** (`registration::issue`, gemeinsam für CLI, Admin-Socket und `CreateInviteRequest`), unter der Store-Sperre:
1. Abgelaufene, nie quittierte Registrierungen verwerfen (`store.purge_expired_registrations`) — sonst hielte ein verfallenes erstes Bundle den Bestand nicht-leer und kostete das nächste die Admin-Rechte bis zum Neustart. Ist der Bestand dann leer, darf `public_host` kein für Beispiele reservierter Name sein (§6.1 Schritt 1): das erste Bundle wäre das erste Zertifikat damit. Danach: sind schon `Config::max_pending_invites` (`limits.max_pending_invites`, Default `2 × max_users`) Nutzer `is_pending` und nicht widerrufen, → `RATE_LIMITED` (2026-09-26): jede offene Einladung ist ein Nutzer, und `users.toml` wird bei jeder Änderung ganz unter der Store-Sperre geschrieben — ein Admin-Zertifikat in falschen Händen konnte die Datei um Millionen Einträge am Tag wachsen lassen. Eine widerrufene Einladung bleibt bis zum Ablauf im Bestand, belegt aber keinen Platz mehr (Folgereview 2026-09-26; vorher bis zu 7 Tage). `CreateInviteRequest` zählt zusätzlich je Admin gegen einen Stunden-Bucket (`limits.invites_per_admin_per_hour`, 20; `Server.invite_budget`); die CLI auf dem Host nicht. `0` schaltet Einladungen per `CreateInviteRequest` ab (`RATE_LIMITED`; 2026-09-27, externes Review: der Bucket rundete 0 auf eine je Stunde auf). Eine abgelehnte Einladung (`NAME_TAKEN`, `RATE_LIMITED` der Obergrenze, `SERVER_ERROR`) hat nichts ausgestellt und gibt ihr Token zurück (Folgereview 2026-09-26).
2. Platzhaltername: der mitgegebene (muss `validate_name` erfüllen und frei sein, sonst `NAME_TAKEN`), sonst `neu-` + 4 Hex-Ziffern, bis einer frei ist.
3. `ca.issue_registration`: frischer P-256-Schlüssel, Subject `CN=<Platzhalter>, OU=ICU registration`, URI-SAN `icu://<public_host>`, EKU ClientAuth, `not_after = now + ttl` (Default 24 h, höchstens 7 Tage).
4. `store.add_registration`: Nutzer mit `CertRecord { registration: true }`; `is_admin = store.is_empty()` — nur vorläufig, endgültig entscheidet die Quittung (Einlösen, Schritt 4). Der Schlüssel wird nicht gespeichert, er verlässt den Server nur im Bundle (`PassportV2`).

**Einlösen** (`session::registration_exchange`): `authenticate` liest `CertRecord.registration` und den SubjectPublicKeyInfo des vorgelegten Leafs. Ist es eine Registrierung, läuft die Sitzung nicht über den Raum:
1. Platz unter den Sitzungen außerhalb des Raums (§6.2) → sonst `close(SERVER_FULL)`; erst dann IP-Ratenlimit (`allow_enroll`, 5/min pro IP, 20/min global) → sonst `close(ENROLL_RATE_LIMITED)`. Eine wegen `SERVER_FULL` abgewiesene Registrierung kostet also kein Budget.
2. `Hello` wie in §6.4 Schritt 2, dann direkt auf den Stream `Welcome { registration: true, users: [], you.session: 0 }`.
3. Schleife, höchstens 120 s: `Ping` → `Pong`; `RenewRequest` → `redeem`; alles andere → `PROTOCOL_VIOLATION`. `redeem`: CN aus der CSR (`csr_common_name`), Schlüssel ≠ Registrierungsschlüssel, Name frei (außer für sich selbst), `sign_client_csr`, dann `store.redeem_registration` — höchstens `REDEEMS_PER_BUNDLE` (5) Einlösungen ohne Quittung, sonst `RENEW_REJECTED`; neues Cert anhängen, Namen übernehmen, Zertifikate früherer, unquittierter Einlösungen widerrufen und als `superseded` markieren (2026-09-26, damit sie nach Ablauf aus Store und CRL fallen statt mit jeder Wiederholung anzuwachsen), ohne quittierten Admin (`has_enrolled_admin`: funktionsfähig und nicht `is_pending`) vorläufig `is_admin` setzen, **ein** Schreibvorgang. Das Registrierungszertifikat bleibt dabei gültig (revidiert 2026-09-24). Nicht-fatale Fehler gehen als `Error` hinaus, die Sitzung bleibt für einen neuen Versuch offen (höchstens 10, dann `RATE_LIMITED_FATAL`).
4. Nach `RenewResponse` wartet der Server bis zu 5 s darauf, dass der Client schließt, statt selbst zu schließen — ein eigenes Close könnte die Antwort überholen. Schließt der Client mit `REGISTRATION_STORED`, hat er das Zertifikat gespeichert: `store.consume_registration` widerruft das Registrierungszertifikat und macht ihn, falls es noch keinen quittierten Admin gibt, zum Admin — im selben Schreibvorgang verlieren alle anderen noch ausstehenden Nutzer ihre vorläufige Admin-Markierung, damit genau einer übrig bleibt (2026-09-24). Jeder andere Ausgang (anderer Code, auch `NO_ERROR` — so schließt quinn eine fallengelassene Verbindung —, Timeout, Abbruch) lässt das Bundle gültig, damit eine verlorene Antwort oder ein gescheitertes Speichern es nicht verbrennt. `authenticate` verbraucht die Registrierung zusätzlich beim ersten Login mit einem echten Zertifikat des Nutzers (Absturz nach dem Speichern, vor der Quittung).

**Client-Zertifikate** (`sign_client_csr`, auch für Renewals): Subject nur der geprüfte CN aus der CSR (als UTF8String neu gebaut), einziger SAN die URI `icu://<public_host>`, EKU ClientAuth, keine Key Usage, `not_before = now − 1 h`, `not_after = now + client_validity_days`, Serial = 16 Byte mit 127 Zufallsbits (das oberste Bit ist 0, damit der DER-INTEGER ohne Füllbyte positiv bleibt); nur P-256 mit SHA-256 und P-384 mit SHA-384 (`ca::parse_csr`, 2026-09-27, externes Review S-3): die Kurve kommt aus dem `SubjectPublicKeyInfo` der CSR, denn rcgen 0.14 leitet den Algorithmus aus der Signatur-OID ab und baut das `SubjectPublicKeyInfo` daraus neu — ein P-384-Schlüssel mit SHA-256-Signatur wurde als P-256 mit 97-Byte-Punkt zertifiziert. `ca::csr_public_key` liefert das `SubjectPublicKeyInfo`, wie es im Zertifikat steht (rcgen-Kodierung nach derselben Prüfung), statt der rohen CSR-Bytes; darauf vergleichen `session::redeem` (frischer Schlüssel) und `session::renew_leaf` (abgelaufenes Zertifikat, eigener Schlüssel). Der CN wird mit x509-parser aus dem rohen DER gelesen (nicht über rcgens `DistinguishedName`, das zwei CNs still zu einem verschmelzen würde): genau einer, als UTF-8 lesbar, `validate_name` erfüllt.

**CRL** (2026-09-24, `protocol.md` §1): `CertRecord.serial` (Hex der Serial, beim Ausstellen gesetzt; alte Einträge ohne) und `UsersFile.revoked_server`/`crl_number` liefern `Store::crl_serials`; `Ca::crl` signiert daraus eine CRL (rcgen, CRL-Nummer aus `Store::next_crl_number`, streng monoton und nie unter der Unix-Zeit in Sekunden, damit ein zurückgespielter Stand nicht unter der Nummer der Clients landet, `nextUpdate` +30 d, nicht erzwungen). `endpoint::server_config` hängt sie an den `WebPkiClientVerifier` (`with_crls`, `only_check_end_entity_revocation`). `endpoint::build_crls` signiert unter derselben Nummer eine zweite CRL nur aus `Store::revoked_server_serials` — die bekommen die Clients (2026-09-26; sie prüfen nur das Server-Leaf, und die volle CRL passte ab ~430 Einträgen nicht mehr in einen Control-Frame). `endpoint::reload_tls` baut beide CRLs und die TLS-Konfiguration neu, setzt sie per `set_server_config` auf alle Endpoints (`Server.endpoints`) und broadcastet die der Clients als `CrlUpdate` — alles unter dem Store-Lock, also in der Reihenfolge der CRL-Nummern (2026-09-27, externes Review S-4: vorher wurde nach dem Lock veröffentlicht, und zwei gleichzeitige Reloads, etwa die stündliche Rotation und ein Login, der Zertifikate ablöst, konnten die ältere CRL in `Server.crl` stehen lassen, die jede neue Sitzung bekam); aufgerufen beim Start (Offline-Widerrufe greifen ab dem ersten Handshake), nach `revoke` (Socket und in-band), nach jeder verbrauchten oder wiederholten Registrierung und nach `rotate-server-cert`. Nie unter dem Store-Lock aufrufen; Lock-Reihenfolge überall Store → CA. Neue Sitzungen bekommen die aktuelle CRL direkt nach `Welcome`.

### 6.4 Session (`session.rs`)

1. `peer_identity()` → `None` → `close(AUTH_REQUIRED)`. Sonst Leaf-DER → SHA-256 → `users.toml`: unbekannt → `AUTH_UNKNOWN_CERT`, revoked → `AUTH_REVOKED`, `disabled` → `AUTH_DISABLED`. (rustls hat Kette und Ablauf schon geprüft.) Zusätzlich wird der Subject-CN des Leafs gelesen und in `Identity` mitgeführt; weicht er vom gespeicherten Namen ab, wird das **nur protokolliert, nie abgelehnt** — der Server bewahrt keine Zertifikats-DER auf und könnte den CN für Bestandszertifikate gar nicht kennen. Der Client gleicht sich selbst an (Nachzügler-Renewal).
2. `accept_bi()` und erstes Frame binnen 5 s — **eine** gemeinsame Frist ab Beginn, nicht je 5 s —, sonst `HELLO_TIMEOUT`. Muss `Hello` sein. Versionen prüfen (`protocol.md` §8): `Hello.minor < MIN_PEER_MINOR` oder SemVer aus `Hello.client` (`icu_proto::client_version`) unter `min_client` bzw. unlesbar → `VERSION_UNSUPPORTED`; dann `minor` aushandeln (`min(client, server)`). `Hello.name` wird ignoriert (`protocol.md` §2.2).
3. Ist der Raum voll (`room.len() >= max_users`), `close(SERVER_FULL)`. Unmittelbar vor `room.join()` werden Revoke und `disabled` unter dem Store-Lock erneut geprüft, und das Lock bleibt bis nach dem Join gehalten: ein Revoke während des `Hello`-Wartens trifft sonst niemanden, weil der Kick nur Raum-Mitglieder sieht. Sonst `room.join()` → Session-ID (monoton; nach 65 535 läuft der Zähler auf 1 um und überspringt belegte IDs, bei leerem Raum beginnt er wieder bei 1), `Welcome { you: UserInfo{user_id, session, name, flags}, users, audio, min_client, minor, caps, is_admin, server_minor }` senden — `name` ist der gespeicherte Name, also der CN des jüngsten Zertifikats, nicht der des vorgelegten —, `UserJoined` an alle anderen. Beides wird unter dem Raum-Lock eingereiht, der das Mitglied einfügt, damit kein Broadcast vor `Welcome` ankommt.
4. Zwei Tasks pro Client: (a) Control-Reader (Frames → `ControlMsg` → Handler), (b) Datagram-Reader (`read_datagram` → `relay::audio`). Video: `accept_uni` in einem dritten Task → `relay::video`. Frame- und Byte-Budget (`relay::VideoBudget`) hängen am Nutzer (`Server.video_budget`), nicht an der Verbindung: bis 2026-09-26 bekam jede Verbindung volle Buckets, und `relay::video` las jeden Frame ganz (`read_to_end`), bevor es ihn abbuchte — ein Sender im Minus schob so bis zu 20 × 512 KiB/s über die Leitung, die dann verworfen wurden. Jetzt stoppt ein Minus den Stream nach dem Header, angenommene Frames werden stückweise abgebucht (`TokenBucket::charge`). Der Audio-Bucket bleibt je Verbindung (≤ 110 × 410 B/s).
5. Ausgehend: ein begrenzter `mpsc`-Kanal (256 Frames) pro Client für Control-Frames (Broadcasts), ein Writer-Task schreibt auf den Control-Stream. Ist der Kanal voll, liest der Client seinen Control-Stream nicht mehr; er wird mit `TIMEOUT` geschlossen, statt dass sein Rückstau im Server wächst. Datagrams werden direkt aus dem Relay per `send_datagram` geschickt (nicht blockierend).
6. Ende: Verbindung geschlossen oder Fehler → `room.leave()` → `UserLeft { session, reason }` Broadcast; `reason` = `NO_ERROR` bei sauberem Close, `TIMEOUT` bei Idle-Timeout oder Transportabbruch, sonst der Code, mit dem der Server geschlossen hat. Die Session-ID wird erst nach einem Zählerumlauf wieder vergeben.

| `Ping` | unverzüglich `Pong { nonce, server_time_ms }`, `server_time_ms` = Unix-Millisekunden UTC. Zählt gegen das Control-Limit. |
| `SetName` | Entfällt. Nicht mehr C→S: Empfang schließt mit `PROTOCOL_VIOLATION`. Umbenennen läuft über `RenewRequest`. |
| `LossReport` | Wert je (Sprecher, Hörer) fortschreiben und den Hinweis neu bilden, siehe §6.5. |
| `KeyframeRequest` | an den Sprecher weiterleiten, siehe §6.5. |
| `RenewRequest` | CSR wie in §6.3 („Client-Zertifikate“) prüfen; der CN **kommt aus der CSR** und ist der gewünschte Name. Drei Fälle, unterschieden durch exakten Stringvergleich gegen den gespeicherten Namen (exakt, nicht `name_key`: sonst liefe eine reine Groß-/Kleinschreibungs-Umbenennung auf dem Zweitgerät als normales Renewal ins Tageslimit): **normales Renewal** (CN = gespeichert, vorgelegtes Cert aktuell) erst im letzten Drittel der Laufzeit des vorgelegten Zertifikats, mindestens ab 30 Tage vor Ablauf (`renew_window`), zählt gegen `last_renew`, ≤ 1/Tag; **abgelaufenes Cert** (renew-only-Sitzung `session::recovery_exchange`, `protocol.md` §2.3.3) nur unter dem gespeicherten Namen und nur auf den Schlüssel des vorgelegten Zertifikats (SPKI der CSR = SPKI des Leafs, sonst `RENEW_REJECTED`; 2026-09-27 — vorher stand das nur in der Doku, geprüft wurde es nicht), über `CertRecord.renewed` des vorgelegten Zertifikats auf eines pro Stunde begrenzt, zählt nicht gegen `last_renew`; **Nachzügler** (CN = gespeichert, vorgelegter CN alt) ist davon ausgenommen und stattdessen über `CertRecord.renewed` des vorgelegten Zertifikats auf einen pro Tag begrenzt; **Umbenennung** (CN ≠ gespeichert) prüft zuerst `name_taken(cn, Some(self))` → `Error(NAME_TAKEN)` und zählt sonst gegen `last_renew`. Vor allem anderen läuft unter dem Store-Lock noch einmal `admit` für das vorgelegte Zertifikat (2026-09-26): seit der Anmeldung kann es widerrufen oder von einem Nachfolger abgelöst worden sein, und `add_cert` prüft nur den Nutzer — eine renew-only-Sitzung auf einer Kopie hätte sonst nach der Ablösung noch einen Nachfolger bekommen. Ein fataler Code beendet die renew-only-Sitzung mit diesem Code. Außerhalb des Renewal-Fensters übernehmen Umbenennung und Nachzügler die Gültigkeit des vorgelegten Zertifikats (`ca::Lifetime::Keep`, im `CertRecord` dessen `issued`/`expires`); eine volle neue Laufzeit (`Lifetime::Days`) gibt es nur im Fenster oder für ein abgelaufenes (2026-09-24). Abgelaufen heißt abgelaufen zum Zeitpunkt des `RenewRequest`, nicht des Handshakes (2026-09-27, externes Review): eine Raumsitzung überlebt das notAfter ihres Zertifikats und durfte danach noch auf einen neuen Schlüssel erneuern. Ein Zeitstempel aus der Zukunft (`last_renew`, `CertRecord.renewed`, geschrieben, während die Uhr vorlief) zählt als lange vergangen, statt jedes Renewal abzulehnen, bis die Uhr ihn einholt (S-7, `session::within`). Die Eindeutigkeitsprüfung liegt **vor** dem Ratenlimit, damit ein belegter Name `NAME_TAKEN` meldet und nicht eine verwirrende Ratenmeldung. Danach `store.add_cert`: Cert anhängen, CN als Namen übernehmen, ggf. den vorgelegten Fingerprint stempeln — **ein** Schreibvorgang, damit kein Crash zwischen zwei Writes einen Nutzer hinterlässt, dessen Name nicht zu seinem jüngsten Zertifikat passt. Gestempelt wird nur beim Nachzügler und beim abgelaufenen Cert: dasselbe Zertifikat kann auf einem zweiten Gerät liegen (Passport), das seinen eigenen Nachzügler noch vor sich hat. Antwort `RenewResponse { leaf_der }`; bei geändertem Namen zusätzlich `room.rename` + `UserRenamed` für **jede** Sitzung dieses Nutzers. Das vorgelegte Cert und alle älteren bleiben gültig, bis das neue sich zum ersten Mal anmeldet; dann widerruft `Store::retire_predecessors` sie (`protocol.md` §2.2 Nr. 10). `CertRecord`s bleiben stehen, auch abgelaufene (sie lassen eine renew-only-Sitzung zu); nur verbrauchte Registrierungszertifikate räumt derselbe Schreibvorgang nach Ablauf weg. |
| `CreateInviteRequest` | Nur wenn `Actor::is_admin` (s. `AdminSetRole`), sonst `Error(NOT_ADMIN)` und nichts weiter; `registration::issue` prüft den Actor unter seinem eigenen Lock noch einmal, weil zwischen beiden Locks eine Herabstufung liegen kann (2026-09-26). Dann der Stunden-Bucket des Admins (§6.3, sonst `Error(RATE_LIMITED)`), dann `registration::issue` (§6.3) und `CreateInviteResponse { bundle, expires }`; ein belegter oder ungültiger Platzhalter → `Error(NAME_TAKEN)`, zu viele offene Einladungen → `Error(RATE_LIMITED)`, ein Fehler ohne Code (Schreibfehler) → `Error(SERVER_ERROR)` (2026-09-26, vorher `NAME_TAKEN`). |
| `AdminSetRole` | Nur wenn `admin::Actor::is_admin` unter demselben Store-Lock wie die Änderung gilt, sonst `AdminActionError(NOT_ADMIN)`: das Zertifikat der Sitzung ist noch zugelassen (`session::admit`: bekannt, nicht widerrufen, Nutzer nicht gesperrt), gehört diesem Nutzer, und der Nutzer ist Admin. Seit 2026-09-26 für alle in-band Admin-Aktionen; vorher nur das `is_admin`-Flag, und eine Aktion, die schon auf den Lock wartete, lief nach dem Sperren oder Widerrufen ihres Absenders noch durch (etwa ein Selbst-Entsperren, das den Kick überholt). Sonst `store.set_admin(target, is_admin)`; bei `LAST_ADMIN` `AdminActionError(LAST_ADMIN)`; ein Fehler ohne Code (Schreibfehler) wird für alle Admin-Aktionen `AdminActionError(SERVER_ERROR)` (`session::admin_answer`, 2026-09-26; vorher `LAST_ADMIN`). Bei Erfolg `AdminSetRoleOk` an den Absender und `UserAdminChanged { is_admin }` unicast an jede eigene Sitzung des Ziels (live, ohne Reconnect). |
| `AdminSetDisabled` | Wie `AdminSetRole`, aber `store.set_disabled(target, disabled)`. Wird dabei deaktiviert, kickt der Server jede laufende Verbindung des Ziels sofort mit `AUTH_DISABLED` (`admin::set_disabled`, dieselbe Operation wie hinter dem Admin-Socket) — kein separater Push, das Schließen ist die Benachrichtigung. Schreiben und Kick geschehen unter dem Store-Lock wie bei `set_role` (2026-09-27, externes Review S-5): vorher kickte `disable` nach dem Lock, und ein gleichzeitiges `enable` konnte dazwischen schreiben — der Nutzer blieb freigeschaltet, flog aber mit dem fatalen `AUTH_DISABLED`. `AdminSetDisabledOk` an den Absender. |
| `AdminRevokeUser` | Wie `AdminSetRole`, aber `admin::revoke_user`: `store.revoke(target)`, Kick mit `KICKED`, CRL neu laden. `AdminRevokeUserOk { user_id, closed }` an den Absender. |
| `UserListRequest` | Nur wenn `Actor::is_admin`, sonst `AdminActionError(NOT_ADMIN)`. Sonst jeden registrierten Nutzer (online oder nicht) als `UserSummary` sammeln (`online` über `room.online_users`, `pending` über `UserRecord::is_pending`), sortiert: online, Admins, übrige, widerrufene, je die neuesten zuerst; `fit_user_list` sucht per Bisektion den längsten Kopf, der mit einer Restzeile (`user_id` 0, `… und N weitere`) in einen Control-Frame passt, falls nicht alle passen (2026-09-26), und sendet `UserListResponse { users }`. |
| unbekannte Variante / Decode-Fehler | `close(PROTOCOL_VIOLATION)`. |

**Letzter-Admin-Schutz** (`store::guard_last_admin`, gilt für `set_admin(_, false)`, `set_disabled(_, true)` und `revoke`, über alle drei Pfade — in-band, Admin-Socket, CLI-Offline-Fallback — identisch, da eine einzige Store-Methode): ein Nutzer zählt als *funktionsfähiger Admin*, wenn `is_admin && !disabled && mindestens ein Cert nicht revoked`. Die Aktion wird nur abgelehnt, wenn ihr Ziel aktuell funktionsfähiger Admin ist **und** danach kein funktionsfähiger Admin mehr übrig wäre — ein bereits deaktivierter oder vollständig revoked Admin zählt nicht mehr mit und blockiert daher nichts. **Gezählt werden nur quittierte Admins** (`!is_pending()`, dieselbe Regel wie `has_enrolled_admin`, die bei der ersten Quittung über den Admin entscheidet; 2026-09-27, externes Review S-1): vorher zählte ein noch eingeladener Admin mit — das erste Bundle, eine vorläufige Einlösung, ein beförderter Eingeladener. Folgen waren, dass ein durchgesickertes erstes Bundle nicht widerrufen werden konnte (`LAST_ADMIN`) und dass der letzte quittierte Admin zurücktreten durfte, sobald er einen Eingeladenen befördert hatte; quittierte dann ein Dritter zuerst, wurde der Admin und die Beförderung verfiel. Ein noch eingeladener Nutzer ist deshalb nie Ziel des Schutzes; befördern darf man ihn weiterhin, er zählt erst ab seiner Quittung. `consume_registration` quittiert für einen gesperrten Nutzer nichts (keine Admin-Markierung, das Bundle bleibt offen, der erste Login nach `enable` verbraucht es).

#### Öffentliche Sitzungszertifikate

Minor 3 ergänzt `PeerCertificateRequest`/`PeerCertificateResponse` (Nr. 38/39). Der reguläre Control-Handler verwendet das bestehende Ratenlimit. `Room::certificate` liest ausschließlich das öffentliche Leaf aus `quinn::Connection::peer_identity` einer aktuell anwesenden Sitzung. Maximal 8192 DER-Bytes, Antwort nur an den Anfragenden. Fehlende/zu große Zertifikate ergeben `None`; Raumlose Registrierungs- und Renewal-Sitzungen erhalten diesen Zugriff nicht. Minor 4 ergänzt `VideoDisplayed`/`VideoViewer` (Nr. 40/41); der Server prüft aktuelle Anzeige- und Kameraberechtigung und leitet höchstens einen Bericht pro Sekunde je Paar weiter. Server und Clients gemeinsam aktualisieren; Mindest-Minor ist 4.


### 6.5 Relay (`relay.rs`)

Audio: siehe `docs/reference/protocol.md §3`. Implementierung: `Bytes` aus `read_datagram`, `BytesMut::from` nur für die 2 Speaker-Bytes, dann `freeze()`; ein `Bytes`-Clone pro Empfänger (Refcount). Das ist der einzige heiße Pfad des Servers (16 Clients × 50 Pakete/s), deshalb prüft er zuerst das Datagram-Ratenlimit (nur der Bucket des Tasks, kein geteilter Zustand) und holt erst dann das Room-Lock, genau einmal — für Absenderflags, Empfängerliste **und** Talk-Spurt-Buchführung zusammen (`room.audio_fanout`) — und schreibt die Empfängerliste in einen Puffer, den der `datagram_task` besitzt und über alle Datagrams wiederverwendet; pro Datagram wird also nichts alloziert. Zähler pro Empfänger für `TooLarge | UnsupportedByPeer | Disabled | ConnectionLost` — das sind die Varianten von `quinn::SendDatagramError`; ein `Blocked` gibt es nur auf `quinn_proto::SendDatagramError` und nie auf der hier benutzten High-Level-API. Zusätzlich setzt der Server `speaking` implizit: erstes Datagram nach ≥ 500 ms Stille → `UserState{speaking=1}` Broadcast, `END`-Flag oder 500 ms ohne Datagram → `speaking=0`. Damit brauchen Clients für den Indicator keine eigene Meldung; ein von Clients in `SetState` gesetztes bit2 wird ignoriert (`protocol.md` §2.1: bit2 ist serverseitig autoritativ).

Video: `session::uni_task` nimmt je Sender höchstens 4 Streams gleichzeitig an (`VIDEO_STREAMS_PER_SENDER`); weitere werden ungelesen mit `stop(RATE_LIMITED)` abgelehnt. Header und Nutzlast zusammen haben `timing.video_frame_timeout_ms` (5 s), danach `stop(RATE_LIMITED)` und Zähler `video_stalled`. Am 12-Byte-Header werden Kamera-Flag, aktiver Sender und Frame-/Byte-Budget geprüft; ein Sender im Minus wird vor der Nutzlast gestoppt. Ein angenommener Frame (≤ 512 KiB Nutzlast) wird vollständig in einen gemeinsamen Puffer gelesen und stückweise abgebucht, auch ins Minus, damit große IDRs durchgehen. Nach dem Lesen werden Kamera-Flag und aktive Sitzung erneut geprüft, bevor `speaker` gesetzt wird.

Pro Sender-Empfänger-Paar hält ein Forwarder höchstens `VIDEO_UNACKED_PER_PAIR` (2) Frames, die der Empfänger noch nicht bestätigt hat, und einen wartenden (2026-09-27, Readiness-Review S3). `finish()` stellt einen Frame nur in die QUIC-Sendewarteschlange; bestätigt ist er erst, wenn `SendStream::stopped()` auflöst (quinn 0.11: `Ok(None)`, sobald alle Daten des beendeten Streams quittiert sind, `Ok(Some(code))`, wenn der Empfänger ihn stoppt). Vorher zählte „1 schreibend“ Frames, die an quinn übergeben waren: ein Zuschauer mit zu schmalem Downlink sammelte, bis Stream-Kredit (132) oder `SEND_WINDOW` erschöpft waren, rund 9–18 s Video, ohne dass je ein Frame verworfen wurde oder ein `VideoCongestionHint` kam. Jetzt wartet der nächste Frame im Slot, und neuere Frames verdrängen ihn oder werden verworfen: der Zuschauer bleibt nahe live (im Test mit 128-kbit/s-Downlink gegen 360 kbit/s Video höchstens ≈ 0,7 s statt 5 s), und die Verwürfe gehen in den Hinweis an den Sender. Zwei decken bei 15 fps eine RTT samt ACK-Verzögerung bis ≈ 130 ms verlustfrei ab; darüber verwirft auch ein sonst gesunder Zuschauer Frames. `open_uni()`, `write_chunk()` und die Bestätigung haben zusammen `timing.video_frame_timeout_ms` ab der Entnahme aus dem Slot; ein Frame, der das überschreitet, wird mit `reset(RATE_LIMITED)` beendet und zählt als `video_dropped_slow_receiver` (nach `finish()` also zusätzlich zu `video_frames_out`, das weiter bei `finish()` zählt). Die Frist des ältesten Frames wird auch unterhalb der Grenze überwacht: vorher nur bei 2 unterwegs, und der letzte Frame vor einer Pause an einen Empfänger ohne Quittung ging erneut hinaus, solange die Verbindung bestand. Ebenso während `open_uni()` und `write_chunk()` des nächsten Frames (`InFlightFrames::settling`, 2026-09-27, zweite Runde des externen Reviews): vorher lief dabei nur die Frist des neuen Frames, und ein unbestätigter Frame davor wurde erst aufgegeben, wenn Eröffnung oder Schreiben des nächsten durch war — bei fehlendem Stream-Kredit also erst mit dessen Frist. Die laufende Operation wird dabei nur weiter gepollt, nie neu gestartet: `write_chunk()` ist nicht cancellation-safe. Endet der Forwarder (Slot geschlossen, Sender weg, Shutdown, Verbindung weg), setzt `InFlightFrames` beim Drop jeden noch unquittierten Frame mit `reset(RATE_LIMITED)` zurück, ungezählt: quinn beendet einen fallengelassenen `SendStream` mit `finish()`, statt ihn zu verwerfen, und würde ihn weiter übertragen (2026-09-27, externes Review; Tests in `tests/slow_viewer.rs`).

**Keyframes** (2026-09-27, S4): Der Slot kennt `VIDEO_FLAG_KEYFRAME`. Ein Keyframe ersetzt, was wartet. Ein Delta wird verworfen statt des wartenden Frames, wenn schon einer wartet — der wartende bleibt decodierbar, ein Delta hinter einem verworfenen nicht, und der wartende kann gerade der Keyframe sein, den der Empfänger braucht. Nach jedem Verwurf eines Paars (im Slot oder unterwegs per Timeout, dann samt wartendem Delta) gehen nur noch Keyframes durch, bis einer im Slot angekommen ist. Vorher konnte ein wartender IDR einem Delta weichen, und der Empfänger bekam danach bis zum nächsten IDR nur Deltas, die er ohnehin verwarf. Der wartende Frame hat noch keinen Stream und braucht deshalb kein `reset`. Video-Streams haben Priorität -1, Control Priorität +1.

Ein Slot gehört zur `stable_id` der Empfängerverbindung. Beim nächsten Frame fallen Slots für ausgeschiedene oder nicht mehr zuschauende Empfänger weg, auch wenn kein Empfänger übrig bleibt. Verlässt der Sender den Raum, schließt `Drop for VideoSender` alle Slots. Schließen verwirft den wartenden Frame und unterbricht auch einen in `open_uni()` oder `write_chunk()` blockierten Forwarder; Shutdown beendet ihn ebenfalls. Video-Empfänger sind nur andere Teilnehmer mit `viewing`, ohne vom Admin erzwungenes Taubschalten. Ohne Empfänger wird der eingehende Frame gelesen und verworfen (`video_dropped_no_receiver`), damit die Flusskontrolle weiterläuft.

**`VideoCongestionHint`** (`protocol.md` §2.2 Variante 16, 2026-09-21): pro Sender (im selben `VideoSender`, keine neue Struktur) eine rollierende Offer/Verdrängungs-Zählung je Empfänger (Verdrängung = der Slot war belegt, und der wartende oder der angebotene Frame wurde verworfen — seit S3 auch, weil der Empfänger nicht quittiert; die Deltas, die danach bis zum nächsten Keyframe übersprungen werden, zählen als `video_slow_receiver`, im Hinweis aber nicht noch einmal, sonst läse sich ein einzelner Verwurf als halbe Überlast), alle 2 s zu einer Verdrängungsrate `Verdrängungen · 1000 / Angebote` je Empfänger verrechnet; der Wert, auf den sich **mehr als ein Drittel der Empfänger** dieses Senders einigt (`loss::agreed`, dieselbe Regel wie bei `LossHint`, unten), wird bei ≥ 20 ‰ Änderung als `VideoCongestionHint { drop_permille }` an den Sender geschickt (2026-09-27, externes Review D-1; vorher das Maximum über alle Empfänger). Vereinfachung: das Fenster schließt nur bei einem eingehenden Frame; hört ein Sender ganz auf zu senden (Kamera aus), bleibt der letzte Hinweis stehen statt auf 0 zu verfallen — harmlos, weil ohne Video nichts mehr anzupassen ist. Der Client speist den Wert in seine Qualitäts-Ladder (`docs/reference/client.md` §8); der Server selbst transkodiert nichts, die Anpassung passiert ausschließlich beim sendenden Client.

`LossReport` → je Sprecher der größte Wert, den mehr als ein Drittel seiner Hörer mindestens gemeldet hat (`loss::agreed`: bei n Hörern der (⌊n/3⌋+1)-größte Report; Hörer = die anderen Teilnehmer ohne Taubschaltung, `Room::audio_listeners`, einer ohne gültigen Report zählt als 0 ‰; jeder Report verfällt nach 6 s) → `LossHint` an den Sprecher, wenn sich der Wert ändert. Bis zu zwei Hörern ist das das Maximum wie vorher, bei drei bis fünf der zweitgrößte, bei sechs bis acht der drittgrößte (2026-09-27, externes Review D-1). Der Verlust, den ein Empfänger misst, ist meist sein eigener Downlink; mit dem Maximum zahlte jeder Sprecher dafür 20 % FEC, und ein Empfänger mit `LossReport { 1000 }` für alle oder ein Zuschauer, der seine Video-Streams nie liest, pausierte absichtlich und dauerhaft jedes Video im Raum. Abwägung: in Räumen ab drei Hörern bekommt ein einzelner verlustreicher Hörer nicht mehr die volle FEC seiner Sprecher; ihn schützen sein Jitter-Buffer und seine PLC, beim Video das Ausdünnen je Paar (§6.5, `VIDEO_UNACKED_PER_PAIR`). Kein Wire-Wechsel, der Client bleibt unverändert. **Der Verfall ist eine Änderung:** fallen alle Reports eines Sprechers weg, sendet der Server `LossHint { loss_permille: 0 }`, sonst bliebe der FEC-Overhead beim Sender dauerhaft stehen. `KeyframeRequest` → an den Sprecher mit `speaker = 0`, ≤ 1/s.

#### Audio-Empfangsfeedback

`audio_feedback::Feedback` speichert Capability-Bits und höchstens einen gültigen
Pegelbericht pro aktuellem Sprecher/Empfänger-Paar. Die Control-Session prüft
Mitgliedschaft, Selbstberichte und Deafen vor der Aufnahme; Housekeeping prüft
diese Regeln erneut, verwirft nach 6 s und sendet höchstens alle 2 s einen Hint.
Beide Peers müssen Bit 0 unterstützen. Die Abstimmungsregel ist eine strikte
Mehrheit um den Median (2 dB Gesamtspanne), unabhängig von der LossHint-Regel.
Unzureichende oder widersprüchliche Berichte ergeben `None`; alte Peers bekommen
keine neue Variante. Session-Ende und Abbruch räumen auch die Feedback-Maps auf.
Wire-Formate und Grenzen stehen in PROTOCOL §2.2; der Server steuert keine Geräte.


### 6.6 Limits (`limits.rs`)

Token-Buckets pro Client (Control 50/s, Audio 110/s, Video 20/s und 400 kbit/s) und pro IP (Registrierungssitzungen 5/min, Handshakes 10/s; IPv6 zählt pro /64, weil ein Host meist ein ganzes /64 hält, IPv4-mapped als IPv4), dazu global (Handshakes 100/s, Registrierungen 20/min, höchstens 256 laufende Handshakes und 256 etablierte Verbindungen, Handshake ≤ 5 s) und je validierter Quelle höchstens 4 laufende Handshakes (16 je IPv6-/48, §6.2). Konfigurierbar als `limits.handshakes_global_per_s`, `limits.max_handshakes` (über der Retry-Schwelle 32), `limits.max_connections` (mindestens `2 × max_users`) und `timing.handshake_timeout_ms`. Abgewiesene Verbindungen ohne Zertifikat (`AUTH_REQUIRED`) loggt der Server nur auf `debug`, damit Scanner das Journal nicht füllen. Überschreitung: Datagram/Frame verwerfen und zählen; bei Control `Error(RATE_LIMITED)` (nicht fatal, Verbindung bleibt), beim dritten Verstoß binnen 60 s `close(RATE_LIMITED_FATAL)` — ein eigener, fataler Code, damit der Client nicht in einen Reconnect-Loop läuft (`protocol.md` §5/§6).

## 7. Logging und Metriken

`tracing` mit `tracing-subscriber` (text/json), Felder: `session`, `name`, `remote` (nur bei Connect/Disconnect, nie bei jedem Datagram). Zähler (atomics, über `status` abrufbar, Summen seit Start): Verbindungen (`connections`), Relay-Datagrams in/out, verworfene Datagrams pro Grund, Video-Frames, Registrierungsversuche (JSON-Schlüssel weiterhin `enroll`). Momentanwerte (2026-09-27, S8): `online` (Raum-Sitzungen), `open_connections` (etablierte Verbindungen, `Server.open_connections`), `handshakes` (laufende Handshakes, `Server.handshakes`), `roomless_sessions` (Registrierung und renew-only). Vorher gab es nur die Summe `connections`, und der Checkmk-Check graphte sie als Momentanwert. Dazu, seit 2026-09-28, `version` und `limits.{max_connections,max_handshakes}`: ohne die Obergrenzen konnte ein Monitor `open_connections` und `handshakes` zeichnen, aber nicht sagen, ob sie nahe am Limit sind. Der Check bildet Raten aus den Zählern gegen seinen vorigen Lauf, geht bei anhaltend hohem Anteil `video_slow_receiver` auf WARN, ab 80 %/95 % der Verbindungs- bzw. Handshake-Grenze auf WARN/CRIT und bei anhaltenden Limit-Drops (`rate`, `control_rate_limited`, `video_rate`) oder Registrierungsfehlern (`enroll.failed`) auf WARN; `com_dropped` zeichnet er nur, weil Portrauschen im offenen Internet normal ist (`deploy/README.md` §5). Das JSON liest er mit `sed`, nicht mit `jq`: neue Schlüssel müssen dokumentweit eindeutig und ganzzahlig sein, und ein Objekt darunter darf kein weiteres Objekt enthalten. Kein Prometheus in v1; `status --json` reicht für einen Checkmk-Local-Check.
